# Commands and protocol

## Files

All in the mod folder (`Kenshi\mods\AutomationHarness\`):

| File | Written by | Meaning |
|---|---|---|
| `enabled.flag` | you | harness on (checked every poll; the background-running switch only at game start) |
| `inbox.txt` | tools | commands, one per line: `id<TAB>command<TAB>arg<TAB>arg...` |
| `outbox.txt` | harness | replies, appended: `id<TAB>ok|error<TAB>detail` |
| `autoload.txt` | tools | one save name, loaded once the main menu is up (deleted after use; reply id `autoload`) |
| `harness.log` | harness | log, recreated each game start |

Several clients may run at once (e.g. a background loop plus a scenario), so
writers follow this protocol (`client/kah.py` `write_command` does it):
create `inbox.txt.lock` exclusively (`O_CREAT|O_EXCL`; a lock older than
30 s is stale and may be removed), wait until `inbox.txt` is gone, write a
temp file unique to the call (`inbox.txt.<pid>.<n>.tmp`), rename it to
`inbox.txt`, delete the lock. Use ids unique across clients (kah.py:
`k<ms>_<pid>_<n>`). The harness polls every 250 ms, renames `inbox.txt` to
`inbox.txt.reading` before reading it, then deletes that copy, so a new
inbox written meanwhile is never lost. Arguments can't contain tabs or
newlines.

## Characters

`<npc>` is one of:
- a name: an exact (case-insensitive) match nearest the player wins, else the
  nearest substring match; bodies near the player are found too
- `#serial/index`: the character's full handle as printed by `spawn`, `chars`, `where` (`#374267584/1234`); resolves exactly. `#serial` alone still works but serials are not unique (a spawned bandit once shared one with an NPC 4.5 km away): if several characters have it, the command is refused with a candidate list. The serial comes first, so a `#(\d+)` capture still gets the serial; capture `#(\d+/\d+)` for the exact form
- `@player`: the first squad member
- `@selected`: the selected character

## Built-in commands

Work at the main menu too: `help`, `status`, `load`, `save` (save needs a game).
Everything else needs a loaded game.

| Command | Does |
|---|---|
| `help` | list all commands, including ones registered by other mods |
| `status` | `phase=menu|loading|chargen|world save=<loaded save> last_saved=<last name saved> paused=... speed=... squad=N player=...` (player = the first squad member, not the selection: use `where @selected`) (`save` = the save loaded this session, by `load` or the game's load menu; `?` until one is seen) |
| `load <save>` | load a save (phase stays `loading` until the new squad is in) |
| `save <name>` | save the game |
| `newgame <start name\|sid> [edit]` | the game's New Game with that start (KAH 21; `SaveManager::newGame`; `find start <text>` gives names and sids, e.g. `find start wanderer`; names match in any case, with or without a leading "The", or the sid); works from the main menu or in a game (the current game is dropped unsaved). Like `load`: `status` reports `phase=loading` until the new world runs, so follow with `wait-world`; `save=newgame:<start>`. The new world opens the game's character editor and waits there (to-do 19: m18 sat at `phase=loading` for minutes): `status` shows `phase=chargen` while it is open, and the harness presses its CONFIRM and accepts the "are you sure" box like a player (it retries every 2 s for up to 2 minutes while the editor builds its widgets; a miss logs the visible buttons; `harness.log` lines `KAH: newgame ...`, plus a `newgame waiting:` line every 10 s with signal/loading/squad/chargen). `edit` leaves the editor open for `ui`/`click`. | `speed <0\|0.5..50> [hold]` | game speed; 0 pauses. `hold`: when the game pauses itself (a raid/demand dialog, a squad event) the harness unpauses and restores the speed after 2 s (log `KAH: speed hold`); any later `speed` ends the hold |
| `chars [radius] [filter]` | characters within radius (default 100) of the player (at most 40). `filter`: `|`-separated case-insensitive substrings of a character's line (e.g. `"[band of bones]|[kral"`), applied before the 40 cap. Each line ends with ` race=<race name>` (not matched by `filter`) |
| `traders [radius]` | characters the game itself treats as traders (`isATrader`), default radius 300; shop keepers in towns, or spawn a trader squad such as `"Skeleton Traders Animals" "Traders Guild"` (a lone "Trader" character doesn't count) |
| `find <character\|squad\|item\|weapon\|armour\|container\|research\|start> <text>` | look up game data by name (`start` = new game starts, for `newgame`) |
| `spawn <template> <faction> [near <npc> \| at x y z] [count n] [dist m] [target <npc>] [size <mult>] [race <filter>]` | spawn characters, or a squad template (`target`: the squad's AI goes for that character; `size`: scale the squad). Reply `spawned <made>/<count> <template>: <name> #serial/index race=<race>, ...`. `race` (characters only): `\|`-separated case-insensitive substrings of the race name, `!substr` excludes (e.g. `race "!reptiloid\|!sharkoloid\|!dragoloid"`); a character whose race doesn't pass is destroyed and rolled again, up to 20 tries each; the reply adds `rerolls=<n>`, and `race-failed: no race matching '<filter>' in 20 tries (rolled <races>)` (an error) when one never matched |
| `stash <item> <n> [near <npc>]` | put items into the nearest storage chest |
| `where <npc>` | name, serial, faction, position, distance, KO/DEAD, ` unique=1` for unique (named, non-template) NPCs (the game's `Character::isUnique`; KAH 13; also in `chars` and every character line) |
| `sections <npc>` | inventory sections (size, equip/container slot) with their items, and the worn backpack |

| `hp <npc> set <flesh\|stun\|band\|derived> <value\|max>` | diagnostics: write one field on every part (the game recomputes derived health only while time runs) |
| `inv <npc>` | inventory incl. worn items and backpack as JSON (works on bodies) |
| `stat <npc> <stat>` / `setstat <npc> <stat> <value>` / `stat <npc> all` | read/set a skill (base and effective; `stat` also prints the game's condition multiplier `mod=` (`MedicalSystem::getHealthStatModifier`, all factors) and each factor alone: `hunger= wounds= dark= robot= weather= gear=`, plus `light=` (`Character::getLightLevel`), so balance windows can prove equal conditions); `all` lists every skill as `name=base(effective)`. Names (KAH 16): strength, toughness, dexterity, athletics, perception, attack (melee_attack), defence (defense, melee_defence), dodge, martial_arts, katanas, sabres, hackers, heavy_weapons, blunt, polearms, crossbows, turrets, weapons, mass_combat, friendly_fire (precision_shooting), stealth, assassination, lockpicking, thievery, swimming, survival, labouring (mining), science (research), engineering, robotics, weapon_smith, armour_smith, crossbow_smith, medic, hive_medic, vet, farming, cooking; derived values: maxcarry, maxrunspeed, currentrunspeed, encumbrance, combatspeed, damageresistance, knockouttime, primaryweapondamage, primaryweaponspeed |

| `iteminfo\|equip\|unequip <npc> <item>` | an inventory item by name; `unequip` moves it to the main inventory (dropped next to the character if there's no room); `equip` first moves anything else worn in the same slot type to the main inventory when the slot is taken (reply adds `replaced=<names>`); `equip failed` adds `race=<race>`, `race_ok=0\|1` (the game's `RaceLimiter::canEquip`: the item's `races` / `races exclude` lists) and `race_no_slot=1` when the race can't wear that slot at all (`noHats`/`noShirts`/`noShoes`) |

| `health <npc> <percent>` | set every body part to a percentage of its max (negative values too) and clear stun damage (`fleshStun` is stun damage: before the PG m29 fix it was set to max, so health/protect left the derived health at 0 and the wounds stat factor at 0.25) |
| `kill <npc>` | every body part to -200% |
| `hunger <npc> [0..300]` | set hunger as the game UI shows it (300 = full), reply `before -> after`; without a value only reads it (`Shay hunger 216.0`) |
| `attack <attacker> <target>` | a real attack order, as a player click gives it |
| `money <npc> <delta>` | add (or with a minus, take) cats |

| `select <npc>` | select the character |

| `give <npc> <item> [n]` | create items in the inventory (items, weapons, armour, containers and artifacts such as Books or Engineering Research; reports how many really arrived, counting every section; a backpack goes on the back if that slot is free, else into the main inventory) |

### Orders, fights and jobs

| Command | Does |
|---|---|
| `order <npc> <task> [target <npc>] [building <name>] [keep]` | give a real AI order, any of the game's 291 tasks by name or number (`FIRST_AID_ORDER`, `LIFT_PERSON_PLAYER_ORDER`, `PUT_IN_CAGE`, `LOOT_TARGET`, `USE_BED_ORDER`, `CHAIN_TARGET`…); `keep` adds instead of replacing orders |
| `tasks [filter]` | list task names with their numbers |
| `fight <a> <b>` | make two characters of different factions fight (their factions go to -100, both get an attack order) |
| `job <npc> <building> [task <name>] [radius <m>]` | add a permanent job at the nearest matching building within `radius` of the npc (default 300, max 5000) (default task: the building's own job, e.g. OPERATE_MACHINERY) |
| `jobs <npc>` / `clearjobs <npc>` | list / remove permanent jobs |

### Buildings and time

| Command | Does |
|---|---|
| `buildings [radius] [filter] [near <npc>]` | buildings within `radius` (default 100, max 5000; at most 60 listed, use a filter for big radii) with distance, position (`pos=x,y,z`, for `teleport <npc> x y z`), owner faction and whether they have an inventory; nearest first (the 60 nearest when there are more) |
| `building <name> [radius]` (alias `production`) | the nearest matching building within `radius` of the player (default 300, max 5000; also `radius <m>`): power (on, has power, battery, output; `current_power`, `wants` = the most it draws, `wants_now` / `needs_power_now` = what it asks the grid for this moment (an idle building asks for 0 and so reads `current_power=0 out_of_power=1.0` even on a full grid), `operators=<n>/<max>` and `needs_operating` (a building that must be worked draws power only while someone works it: give it a worker with `job`), `battery_fed`; the town power grid it is in: `grid="<town>"`, `grid_role=consumer|generator|battery|none`, `grid_power=<now>/<max>`, `grid_needed`, `grid_battery=<charge>/<max>`, `grid_members=<n>in/<n>out/<n>bat`, `player_town`; `grid=none` = in no town, so nothing powers it; `supplied=1` after `power … supply`), production (product, quantity, state, inputs), farm state, inventory sections |
| `produced <building> [reset] [radius <m>]` | units a production building (mine, stone processor, refinery: anything with a production output) made, whether or not workers already hauled them away. The first call starts tracking (reply `tracking …`); later calls report `produced=<n> removed=<n> output_now=<n> game_hours=<h> per_game_hour=<rate> samples=<frames sampled>` (buildings are keyed by handle index/serial; harness.log `KAH: produced track key=…` when tracking starts); `reset` reports and restarts the window. How: the output quantity (`getCurrentProductionQuantity`) is sampled every frame, rises count as produced, drops as removed; only a haul and a production step in the very same frame net out (undercount). Up to 32 buildings; a load clears tracking. Farms may not report through this output |
| `power <building> on\|off\|charge\|drain\|supply\|unsupply [radius <m>]` | switch power; `charge` fills a battery, `drain` empties one (read `battery=<charge>/<max>` in the reply) (that only helps if the battery is in the same town grid as the consumers: check `grid_role`); `supply` (test cheat, KAH 10) keeps the building at full power whatever its grid has: its `current_power` is set to what it wants right after every town power-grid update (hook on `Town::updatePowerGrid`) and every frame, until `unsupply` or the game restarts (not saved; refused for buildings that use no power) |
| `fill <building> <item> [n] [section <name>] [radius <m>] [topup] [optional]` | put items into a building's inventory (inputs, storage); reports how many fitted. With `topup` a refill where nothing fits but the building already holds the item answers ok (`full (topup): ...`), so a balance window's refill of a full bench input is not a failure. `optional` also never fails when nothing fits and nothing is held (`nothing fitted (optional): ...`: periodic refills during a long craft, after the queue finished) |
| `build <building name\|sid> [near <npc> [dist m] \| at x y z] [faction <f>]` | create a **finished** building or furniture (`Bed`, `Prisoner Cage`, ...) through the game's factory (`RootObjectFactory::createBuilding`, completed). Data is looked up like `find` (exact name or string ID, else a unique partial name). Default place: `dist` 10 (max 200) along x from the npc (default the player's first squad member); height: the npc's (or the given) y, or the terrain height at x,z when that is within 20 of it; the factory adds the terrain height to the y it gets, so the harness compensates and checks the result (one rebuild if it is off by more than 5; the reply warns if it still is). Identity rotation, no town. Owner: the player's faction unless `faction`; the building's own faction is read back after creation (set again if the factory gave it another one, `(faction set after creation)`), and the command fails with `... but its faction is X, not Y` if it still differs. Reply: name, serial, `pos=x,y,z`, the building's real faction. Refused with `refused: <name> (<sid>) …` (KAH 12), because the game crashes on them: a storage building (functionality `function` 2, Resource storage) whose template has `has inventory` false (it gets no inventory and the game reads it: Biofuel Distillery `43875-Newwworld.mod` crashed at `kenshi_x64.exe+0x2988b5` about 10 s after the next load), and sids on a deny list (`BuildDeniedSid` in `src/BuildArgs.h`, now just that one). In this install's load order the Distillery is the only building the template rule matches |
| `unbuild <name> [radius]` | destroy the nearest building that `build` made this session (name contains the text, within `radius` of the player measured on x,z, default 300, max 5000) via `GameWorld::destroy`; other buildings are never touched |
| `time` | game hours, day, time of day, speed |

Building names match the nearest exact name, else the nearest name containing the text. `radius` is above 0 and at most 5000; anything else is refused.

Client side: `kah wait-game <minutes> [timeout_s]` waits for game time to pass.

### Scenario runner (client side)

`kah run <file> [--csv out.csv] [--stop]` runs a test file, one step per line (`kah run --help`):
a command must answer ok, `! command` must answer error, `command ~ regex` must match;
`@sleep`, `@wait-world`, `@wait-game <min>`, `@until <s> command ~ regex`,
`@set NAME command ~ (group)` (use `${NAME}` later), `@log <file> ~ regex` (new lines since the
run started; `@log-wait <s> <file> ~ regex` polls every 1 s until one matches), `@echo`, `@any <step> ~ regex || <step> ~ regex` (alternatives in order until one passes; an alternative may be an `@log`/`@log-wait` step or an `@set NAME <cmd> ~ (group)` capture (a non-matching one sets nothing), e.g. wait for progress, else re-issue the order: a state the game
reaches by either of two paths, e.g. a crafted item still in the bench output or already hauled by the worker). See `scenarios/example.txt`.
Once the game was in the world, a step that finds it back at the main menu (no `load`/`newgame` sent since; e.g. the whole squad died) ends the run with one `ABORT at line N` line; the remaining steps go to the CSV as FAIL "not run". An `@sleep` of 60 s or more asks `status` every 30 s and ends early then.

Stats: labouring, science, engineering, robotics, weapon_smith, armour_smith,
crossbow_smith, medic, turrets, farming, cooking, stealth, athletics,
assassination, swimming, perception, lockpicking, thievery, plus maxcarry,
maxrunspeed, currentrunspeed, encumbrance.

## Notes

- Weapons can't be created directly (`give`, `stash`, `buy`, `packput`, `craftfinish`): the game's
  item factory refuses them. Make them the real way: `research` + `craft` (see above). `find` shows exact names;
  items can be named by game-data string ID too (`find` prints `sid=`).
- Same-faction NPCs ignore `attack` orders against each other.
- Characters teleported next to a hostile squad get attacked.
